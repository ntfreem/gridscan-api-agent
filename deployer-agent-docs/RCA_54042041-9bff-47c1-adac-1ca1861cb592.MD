# RCA — "Crawl Sub-pages" / crawl-stream not working (production)

## Symptom
On production, enabling the "Crawl Sub-pages" toggle and clicking "Crawl & Save" clears the form but nothing happens — no progress bar, no toast, no scraped pages. Frontend calls `POST /api/knowledge/sources/url/crawl-stream` as an SSE stream.

## Verdict
**Frontend source bug** (wrong auth token key in the SSE helper). NOT a deploy-staleness issue, NOT a backend crash, and NOT an SSE proxy/ingress buffering issue.

## Evidence
1. **Latest code is deployed / route exists.**
   - Backend: `backend/server.py:3576` — `@api_router.post("/knowledge/sources/url/crawl-stream")`.
   - Frontend: `frontend/src/pages/KnowledgeBase.js:349` — calls the endpoint via `consumeSSE(...)`.

2. **Backend logs (active run 54042041), the endpoint returns 401, not 5xx:**
   ```
   POST /api/knowledge/sources/url/crawl-stream HTTP/1.1" 401 Unauthorized ×2
   ```
   Sibling endpoints through the shared axios client succeed in the same session:
   ```
   GET  /api/knowledge/sources            200 OK
   POST /api/knowledge/sources/url        200 OK
   ```
   => The request is rejected at authentication, before any streaming begins. A proxy/buffering problem cannot produce a 401, so `X-Accel-Buffering: no` is irrelevant here.

3. **The token-key mismatch (root cause).**
   - SSE helper reads the wrong key — `frontend/src/pages/KnowledgeBase.js:300`:
     ```js
     const token = localStorage.getItem("token") || sessionStorage.getItem("token");
     ...
     headers: { "Authorization": `Bearer ${token}`, "X-Instance-ID": instanceHeader }
     ```
   - The JWT is only ever stored under `bf_token` — `frontend/src/context/AuthContext.js:84`:
     ```js
     if (tokenVal) localStorage.setItem("bf_token", tokenVal);
     ```
     There is no code anywhere that does `setItem("token", ...)`.
   - The working path (axios) reads the correct key — `frontend/src/utils/api.js:10`:
     ```js
     const token = localStorage.getItem("bf_token");
     const instanceId = localStorage.getItem("bf_instance_id");
     ```
   Because `"token"` is never set, `consumeSSE` sends `Authorization: Bearer null`; the backend `get_instance_access -> get_current_user` rejects it => 401. The `fetch` throws on `!resp.ok`, the stream never opens, so no progress events / no scraped pages.

## Fix (Code — E1 applies in source, then redeploy)
In `frontend/src/pages/KnowledgeBase.js`, `consumeSSE` (~line 300), read the JWT from the same key the axios client uses:
```js
const token = localStorage.getItem("bf_token");
```
(Optional consistency, send the instance header from the same source axios uses, `localStorage.getItem("bf_instance_id")`, though `selectedInstance?.id` is currently the same value and is not the cause of the 401.)

This same bug affects the other `consumeSSE` caller, `POST /api/knowledge/sources/bulk-rescrape` (KnowledgeBase.js:385) — it will 401 for the same reason; fixing the shared helper fixes both.

## Verification notes
- Verified the source mismatch directly in the deployed run's code via sandbox (eph pod on run 54042041).
- Verified the 401s in production backend logs for the active run.
- I did NOT fire a fully-authenticated request from the sandbox (no production JWT is available there), but the token-key mismatch deterministically explains the observed 401s.
