# RCA — Pre-existing data missing from UI after V2 redeploy (rag-search-dev)

## Symptom
After the latest redeploy, existing production data (bots/organisations) disappeared from the UI, but bots still respond to messages — suggesting data is in the DB but not displayed.

## Verdict
Data is NOT lost. The V2 refactor repointed the UI/API to new, empty V2 collections, but the one-time V1→V2 migration script was never executed. All original data is intact in the V1 collections.

## Evidence

### Production DB (db: rag-search-dev-test_database, active run 959780ea)
V2 collections (what the new UI reads) — ALL EMPTY:
- `organisations` = 0
- `bots` = 0
- `connections` = 0
- `connected_accounts` = 0

V1 collections (original data) — INTACT:
- `bot_instances` = 9  (e.g. "James - Support Agent", "Test Instance", created Mar–Apr 2026)
- `users` = 5  (1 with role=superadmin)
- `discord_config` = 6 active (`is_active:true`)
- plus `bot_config`, `telegram_config`, `zendesk_config`, `knowledge_sources`, `conversations`

### Code path (backend/)
- `org_routes.py` → `GET /v2/orgs` queries `db.organisations` (empty) → sidebar shows nothing.
- `bot_routes.py` → `GET /v2/orgs/{org_id}/bots` queries `db.bots` (empty).
- `migrate_v2.py` exists and is the intended V1→V2 migration (bot_instances→bots, discord/telegram/zendesk_config→connected_accounts+connections). Header: "Run: python3 migrate_v2.py", "SAFE: Non-destructive … Repeatable — skips records that were already migrated."
- `migrate_v2` is NOT imported or invoked anywhere: `grep migrate_v2` returns only its own file; not referenced in `entrypoint.sh` or `Dockerfile*`.
- `server.py` `@app.on_event("startup")` only creates V1 indexes, seeds the admin, and runs an unrelated V1 `instance_id` backfill. It does NOT call the V2 migration.

### Why bots still respond
The Discord/Telegram runtime in `server.py` startup still reads the V1 `discord_config` collection (`find({"is_active": True})`) — 6 active configs — so messaging keeps working off V1 regardless of the empty V2 collections.

## Root cause
The V2 multi-tenant refactor switched the sidebar/UI and its API to the `organisations`/`bots`/`connections`/`connected_accounts` collections, but `migrate_v2.py` (which populates those from the V1 `bot_instances` + per-provider config) was never wired into the deploy/startup and was never run. The V2 collections are therefore empty while all V1 data remains present.

## Suggested fix (Code — E1)
1. Populate the V2 collections from V1 by running the migration against production. The cleanest deployable fix: invoke the migration from `server.py`'s startup (e.g. `from migrate_v2 import migrate; await migrate()` inside `startup_event`, guarded so it runs once). This is safe — the script is explicitly idempotent/non-destructive and skips already-migrated records, and the required `superadmin` user exists (precondition met).
2. Redeploy. After startup runs the migration, verify `organisations`, `bots`, `connected_accounts`, `connections` are populated and the sidebar renders the existing bots.

Note: the migration needs the production `MONGO_URL`/`DB_NAME` (present in the prod pod env), so it must run inside the deployed app — it cannot be run from the deployer sandbox (no prod secrets there). No DB data needs to be edited manually; nothing was deleted.
