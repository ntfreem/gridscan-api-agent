# RCA — KB "corrupted/binary" content for scraped URLs (Ouroboros & others)

## Symptom
The bot reports KB content as "unreadable/corrupted binary data" for the Ouroboros consensus
page (`https://developers.cardano.org/docs/developers/curriculum/fundamentals/consensus-and-ouroboros/`,
3 parts / 16.3k chars, instance_id `fc19c65d-b74e-4d6f-9496-e4b4d6984a96`). Re-scraping the
same URL from preview yields ~11k chars of clean text.

## What I verified (prod DB, active run 58ee9d04)
`knowledge_sources`, instance `fc19c65d-b74e-4d6f-9496-e4b4d6984a96`:

- **Ouroboros page — all 3 chunks are binary garbage.** `content` is full of null bytes
  (`\u0000`), control bytes, and UTF-8 replacement chars (`�`). It is NOT HTML, NOT JavaScript,
  NOT base64 — it is raw binary / encoding garbage.
- Sampled other URLs:
  - `https://cips.cardano.org/cip/CIP-30` (part 1/5) → **GARBLED** (same binary garbage)
  - `https://developers.cardano.org/docs/developers/curriculum/fundamentals/overview/` (part 1/2) → **GARBLED**
  - `https://github.com/cardano-foundation/cardano-dev-skills` → **CLEAN readable text**

So corruption is **widespread across the cardano.org-hosted pages** (both `cips.cardano.org`
and `developers.cardano.org`) but the GitHub page is fine. The split is by origin server, not
by page.

## Root cause — Brotli responses stored undecoded
Scraper: `backend/server.py` → `scrape_url_source` (~line 3222).

1. Line ~3231 manually sets a request header: `"Accept-Encoding": "gzip, deflate, br"` —
   advertising that the client accepts **Brotli (`br`)**.
2. `requirements.txt` pins `httpx==0.28.1` but does **NOT** include `brotli`/`brotlicffi`
   (nor `zstandard`). Verified in-sandbox: with no brotli lib, httpx's
   `SUPPORTED_DECODERS = ['identity', 'gzip', 'deflate']` — **`br` is absent**, so httpx
   cannot decompress a Brotli response.
3. The cardano.org sites (CDN-served) honor the `br` advertisement and return
   `Content-Encoding: br`. httpx passes the raw Brotli bytes through **undecoded**, and
   line ~3267 `html_text = resp.text` decodes those compressed binary bytes as UTF-8 →
   the null-byte + `�` garbage that gets chunked and stored into `knowledge_sources.content`.
4. The GitHub page is clean because github.com returned gzip (which httpx decodes natively).

### Reproduction (eph sandbox, this run's source)
- Confirmed `httpx==0.28.1`, and `brotli`/`brotlicffi`/`zstandard` all absent from the image.
- Confirmed `httpx._decoders.SUPPORTED_DECODERS == ['identity','gzip','deflate']` (no `br`).
- Brotli-compressed a sample string and decoded the compressed bytes as UTF-8 → produced
  the exact same class of garbage (`\x1b\x1b\x02���t...`, null/control bytes + `�`) as the
  stored Ouroboros chunks.

## Fixes
### Code (E1) — pick either; (a) is the robust fix
(a) Add `brotli` (and ideally `zstandard`) to `backend/requirements.txt`. httpx then
    auto-decodes `br`/`zstd` responses and `resp.text` returns clean text.
(b) OR remove `br` (and `zstd`) from the manual `Accept-Encoding` header at
    `server.py` ~line 3231, leaving only `gzip, deflate` — servers then won't send Brotli
    and httpx handles the rest.
- Recommended: do (a) (keeps Brotli support working) — optionally also keep the header honest.
- Defensive extra: before storing, reject/flag content that is non-decodable (null bytes /
  high ratio of `�`) so corrupt scrapes never silently enter the KB again.

### User (after the fix is deployed)
- The already-stored corrupted chunks will NOT self-heal. After the code fix is redeployed,
  **re-scrape the affected cardano.org URLs** (Ouroboros, the CIP pages, the curriculum pages)
  to overwrite the garbage chunks with clean text, then verify the bot answers correctly.

## Not the cause
- Not a secret/env issue, not a tier/resource issue, not infra. The app and DB are healthy
  (live URL returns 200; DB reachable). Purely a scraper content-decoding bug + stale corrupt data.
