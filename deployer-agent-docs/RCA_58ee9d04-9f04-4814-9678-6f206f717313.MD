# RCA — "API Tester" KB retrieval concern (rag-search-dev)

## Problem statement
User reports the bot may not be "seeing" all KB articles for the **API Tester** instance (~65 sources, 2–4 parts each). Concern: is the MongoDB `$text` index set up so `search_knowledge` uses relevance search, or is it falling back to loading the first 100 chunks by priority (which would miss articles)?

## Environment
- Deployment: `rag-search-dev` (active run `58ee9d04-9f04-4814-9678-6f206f717313`)
- DB: `rag-search-dev-test_database`, collection `knowledge_sources`
- API Tester instance: bot_instances `_id=6aecb38b30597a38cbbb4624`, **`instance_id=fc19c65d-b74e-4d6f-9496-e4b4d6984a96`** (chunks link by the UUID `instance_id` field, NOT the Mongo `_id`).

## Findings (all evidence from mongo_query, read-only)

**1. Text index — EXISTS and is correct.**
`list_indexes` on `knowledge_sources` returns `title_text_content_text` — a v3 text index with `weights: {title:1, content:1}`, `default_language:english`. So `$text` search is available; the no-index fallback path in `search_knowledge` is NOT being taken.

**2. Document count — healthy, within expected range.**
`count({instance_id: fc19c65d...})` = **195** chunks. Expected 130–260 (65 × 2–4). 195 fits comfortably.
(Collection total across all 5 instances = 305.)

**3. Sample text search — returns relevant results.**
`count({$text:{$search:"stakepool stake pool"}, instance_id: fc19c65d...})` = **26** matches. Sample titles returned are on-topic: "Cardano Accounts API (part 1..10/10)", Cardano staking/governance curriculum pages — confirming relevance-ranked retrieval works.

**4. is_active — no stuck-inactive chunks.**
`count({instance_id: fc19c65d..., is_active:false})` = **0**. `count({..., is_active:true})` = **195** = full set. Every chunk is active.

## Root cause
**No defect found at the index/DB layer.** The text index is present and functioning, all 195 chunks are active, and `$text` queries return relevant ranked results. The bot is using `$text` relevance search, not the first-100-by-priority fallback the user feared.

## If the bot still "misses" articles
That would not be an index problem. The likely lever is the **top-N result limit inside `search_knowledge`** (how many ranked chunks are passed to the LLM context) and/or query phrasing — i.e. relevance search is working but only the top matches are surfaced by design. This is a code-side retrieval-tuning consideration for E1, not an infra/index fix. No reproduction was run in a sandbox (requires live DB + app wiring).
